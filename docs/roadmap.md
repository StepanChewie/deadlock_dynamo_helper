## 2. Главный вывод дня: мониторинг смотрел не туда

Контейнер был нетрудоспособен **30 часов**, и никто не заметил. Разбор:

- **Uptime Kuma смотрел на HTTP-эндпоинт** и всё это время получал `200` — потому что Node однопроцессный и событийный: он обслуживает запросы, **не форкая процессы**. Сервис был «зелёным».
- **Docker healthcheck форкает `node -e`** — и падал 1843 раза подряд. Красный статус был виден только в `docker inspect`.

То есть отказ был **невидим для существующего мониторинга по построению**. Это не «добавить алерт», это выбор правильного сигнала: HTTP-код здесь не является признаком здоровья. Единственный сигнал, который поймал бы это сразу, — счётчик задач cgroup.

## 6. Открытые решения (нужны до старта фаз 2–5)

1. **Удалять `deadlock-live-events-1`?** Он не используется и держит живой ключ. Удаление необратимо.
2. **Ротировать `DEADLOCK_API_KEY` сейчас** — или сначала закончить остальное, чтобы не перезапускать api дважды?
3. **DuckDNS остаётся production-хостом?** Если да — PR 10 должен проверять «сборка получила явный `OVERWOLF_API_BASE_URL`», а **не** «origin не duckdns»: сейчас это разные утверждения, и второе сломает легитимную сборку.
4. **Сколько тегов образов держать?** Предлагаю `current` + 3 последних по коммиту — этого хватает для отката.
5. **Чистить ли общий build cache (20 ГБ)?** Он делится с `aboba-telegramovich` и `slovakia-bot`; цена — более медленный первый деплой.
